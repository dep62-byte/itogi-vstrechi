# Порядок работы и JSON

Для нового пользователя обязательный минимум — текст встречи, имя и дата. Оффер и библиотека уже приложены. Не просить ручную подготовку файлов, которые агент может найти, скачать или создать сам.

## Макеты

| type | Обязательные поля | Ограничения |
|---|---|---|
| title | title, body, evidence | body до 300 символов |
| bullets | title, bullets, evidence | 1–3 полных мысли до 220 символов |
| steps | title, bullets, evidence | 1–3 действия с ответственными |
| case | title, caseId, application, evidence | текст/скрин из cases.json; произвольный result запрещён |
| table | title, headers, rows, evidence | 2–3 колонки, до 5 строк; ячейка до 100 символов |

Заголовки до 100 символов. Это грубые предохранители, а не гарантия вёрстки: визуально проверять всё. Длинную мысль сначала сократить, затем разделить слайд. Для иной композиции скопировать scripts/deck.mjs в папку встречи и изменить там, сохранив размеры шрифта и нативные объекты.

`facts` описывает только факты текущей встречи. Пример для цены: `{"id":"price","owner":"OFFER","statement":"Тариф обсуждался","source":"transcript:00:42:10","status":"APPROVED","claimId":"PRICE-1"}`. На верхнем уровне — `commercialDiscussed: true`. Цена всё равно сверяется с текстом текущего реестра; наличие этого флага само по себе не доказательство.

`evidence` — массив ID фактов. Notes не должны содержать сырой транскрипт и личные данные. В notes можно дать источник и короткое объяснение выбора.

## Смысловая проверка перед сборкой

- У каждой цифры есть источник, единица и период.
- CLIENT не смешивается с BB. DERIVED содержит формулу и источники.
- Цена обсуждалась, совпала с реестром; скидки и внутренние часы инженера не печатаются.
- APPROVED не означает «печатать весь исходный абзац»: сохранить условия, убрать внутренний комментарий источника.
- Условие должно быть в видимом тексте. Enterprise: «финальный состав и стоимость по ТЗ»; EVIDENCE: «по данным BB» или «оценка участника» и ограничение переноса.
- Просроченный календарь и неподтверждённая будущая дата не попадают в предложение.
- На каждую важную боль есть прямой кейс или явно отмеченный EVIDENCE_GAP.
- Ссылка на кейс — доказательство механики; эффект не выведен из чисел на изображении.

## Проверка визуала

Если доступен LibreOffice: отрендерить локальный PPTX в PDF до upload. Если он недоступен, разрешена загрузка для предварительной облачной проверки. Затем всегда экспортировать Google Slides и проверить импорт.

Команды просмотра для среды с Poppler:

```sh
pdftoppm -scale-to 1600 -png current-cloud/cloud.pdf current-cloud/page
node scripts/verify.mjs current-cloud 13
```

Показать агенту все page-*.png, рассмотреть кейсы и таблицы полноразмерно. Если просмотр файлов средой не поддерживается, QA заблокирован; даже при structuralQA passed финал не объявлять.

После проверки агент сохраняет в рабочей папке qa-final.json: ID, pdfSha256 из qa-structure.json, visualQA passed, contentQA passed, дата. Только для реально просмотренного последнего экспорта. При любом изменении новый export и QA.

## Обновление

1. Export текущего ID в отдельную папку.
2. Прочитать облачную версию и составить local manual-edits.json: изменение, слайд, как сохраняем.
3. Сохранить эти изменения в редактируемом PPTX; продуктовые claims перепроверить.
4. Upload с исходной sourceIdentity и baseline.json из export.
5. Повторный export + структурная и визуальная проверка.

Несколько продавцов не должны одновременно править одну встречу. Между проверкой metadata и PATCH есть небольшое окно гонки; Google Drive upload не является транзакционным редактором. Для каждого клиента один ответственный.
